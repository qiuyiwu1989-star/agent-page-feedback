# 设计说明

## 组成

```
浏览器（团队成员）                         服务器                              AI agent
┌────────────────────────┐   HTTP    ┌──────────────────────────┐   HTTP   ┌──────────────┐
│ 网站页面                │ ───────▶ │ fb_server.py              │ ◀─────── │ 读 export.md │
│  └ fb-loader.js（很小）  │          │  /api/fb/items …          │          │ 改网站        │
│     └ feedback.js       │ ◀─────── │  /api/fb/files/<id>       │ ───────▶ │ 回写状态      │
│        └ fb-media.js    │          │  /api/fb/client/*（前端）  │          └──────────────┘
│           └ html-to-image│          │  SQLite + files/ 目录      │
│ 汇总页 feedback.html     │          │  可选：推送通知（飞书等）   │
└────────────────────────┘          └──────────────────────────┘
```

## 一、截图

### 为什么在浏览器里截

- **成本低**：服务器上不用装浏览器。
- **所见即所得**：截的就是用户眼前的页面状态，包括登录后、展开后、滚动到的位置。
- **立刻可见**：截图随批注一起提交，用户提交前就能看到、删掉或替换。

### 步骤（`client/fb-media.js` 的 `capture`）

1. **选区域**：从点选的元素 `el` 开始往上找祖先元素 `box`。满足以下任一条件就停：
   - 祖先比视口宽，或高过 1100 px：停在上一层；
   - 祖先宽至少 `max(520, 元素宽 × 1.8)`、高至少 `max(260, 元素高 × 1.8)`：取这个祖先。

   效果：点一个按钮，会截到按钮所在的那一块；点一整个版块，就截这个版块。
2. **渲染**：`htmlToImage.toCanvas(box, { pixelRatio, skipFonts: true, filter })`。
   - `pixelRatio` 让图片宽度不超过约 1400 px。
   - `filter` 去掉批注界面自己（`#apf-host`）。
   - 背景色取最近一个不透明祖先的背景，避免透明。
   - 跨域图片用 1 × 1 占位图代替，避免整张截图失败。
3. **标注**：按 `el` 和 `box` 的相对位置，在 canvas 上画橙色描边和 10% 透明底色；在点击位置画一个带白边的橙色圆点。
4. **裁剪**：区域太高时，只保留元素上下各约 300 px，高度不超过约 1100 px。
5. **导出**：`toDataURL('image/jpeg', .82)`，随批注一起提交（`shot` 字段，data URL）。
6. **超时与失败**：9 秒没截完就放弃，提示用户手动添加图片；提交按钮最多等截图 9.5 秒。

### 已知限制

- html-to-image 是把 DOM 放进 SVG 再画出来，个别效果（`backdrop-filter`、部分混合模式、跨域字体）可能和实际显示略有差别。
- `<canvas>`、`<video>` 会取当前帧；跨域且没有 CORS 头的图片会变成占位。

截得不理想时，用户可以删掉截图，粘贴一张系统截图代替。

### 补拍（`tools/backfill_shots.js`）

接入前的批注，或者截图失败的批注，可以在服务器外用 Playwright 补拍：

1. 按批注时的屏幕尺寸（`vw × vh`）打开批注时的页面地址（`url`）。
2. 找元素：先用选择器；选择器指到的文字和引用对不上时，按引用文字找；都不行，按原坐标 `px, py`。
3. **先滚动到位，等 1.8 秒，再量位置。** 页面有滚动进入的淡入动画、懒加载图片时，立刻量会偏，或者截到一片空白。
4. 用固定定位的覆盖层画框和圆点，在视口内裁剪截图，然后上传到 `POST items/<id>/shot`。同一条批注的旧截图会被替换。
5. 在批注下留一句说明。已经改好的批注，补拍到的是修改后的样子，要写清楚。

## 二、同步

- **单一数据源**：所有数据只存在服务器上。浏览器、汇总页、agent 都通过同一套接口读写。各端不保存数据副本，所以没有合并冲突。写操作在服务端加锁，按顺序执行。
- **批注条**（`feedback.js`）：
  - 打开时拉取本页的批注：`items?page=页面标识`；
  - 每 60 秒刷新一次，页面不可见时跳过；
  - 单页应用的 `#/` 路由变化时重新拉取；
  - 每 1.5 秒按元素的最新位置挪一次编号标记，这一步不重新请求。
- **页面标识**：「相对网站根路径的路径 + 查询参数 + `#/` 路由」，并去掉 `fb`、`fbid`、`v`、`utm_*` 等参数。同一个页面无论从哪里打开，都是同一个标识；同一套模板的不同详情页（如 `?id=1`、`?id=2`）分开计算。
- **定位**：
  - 选择器：优先用唯一的 `id`，否则用 `标签:nth-of-type` 路径。
  - 点击位置在元素内的比例 `rx, ry`。
  - 引用文字：划选的文字，或元素前 120 个字。
  - 绝对坐标 `px, py`，作为最后的兜底。

  页面改版后，按「选择器 → 引用文字 → 坐标」的顺序找回位置。用到坐标时，在卡片上提示「页面内容已变化」。
- **事件即记录**：改状态时自动追加一条 `kind = status` 的回复（谁、改成什么、说明）。时间线、复盘报告、「从提出到改好的平均用时」都由这些记录算出来。
- **推送**：设置 `FB_NOTIFY_URL` 后，新批注、新回复、状态变化会在后台线程推送。默认是飞书卡片格式，`FB_NOTIFY_KIND=json` 时推送原始 JSON。消息里不含口令。

## 三、存储与读取

### 数据表（SQLite）

| 表 | 内容 |
|---|---|
| `items` | 批注：页面标识、页面地址、标题、选择器、引用、坐标、屏幕尺寸、设备、类型、优先级、正文、作者、浏览器 id、状态、时间；软删除 |
| `replies` | 回复、状态变化和验收记录：`kind` 为 reply、status、review（提交验收）、accept（通过）、reject（打回）、publish（上线）；验收包的预览地址和阶段在 `meta` |
| `files` | 附件索引：所属批注 / 回复、种类（shot / image）、类型、大小；文件本身在 `files/` 目录，用随机文件名 |
| `decisions` | 逐条确认的当前结果（范围、条目、选择、说明、谁、何时） |
| `decision_log` | 逐条确认的全部历史 |

### 身份与权限

- **口令**：
  - 团队口令：可以批注、回复、改状态、读取附件；
  - 管理员口令：另外可以删除、修改任何人的批注。
- **姓名**：自己填写，用于显示。
- **浏览器 id**：随机生成，存在浏览器本地，用来识别「自己写的批注」，自己的可以修改和删除。
- 这套设计适合团队内部和项目早期。需要正式账号时，可以在反向代理层接入统一身份认证，再把用户名填进 `X-FB-Name`。

### 安全

- **限流**：口令错 10 次锁定 10 分钟；每个 IP 每分钟最多写入 120 次。
- **附件**：按文件头判断类型，只接受 PNG / JPEG / WebP / GIF；截图不超过 2.5 MB，其他图片不超过 4 MB，单个请求不超过约 30 MB。附件读取同样要口令，页面先带口令 `fetch` 回来，再生成 blob 地址显示，所以附件地址泄露也不能直接打开。
- **页面渲染**：所有用户输入在显示时都做 HTML 转义。
- **前端文件**：在 `client/` 目录内提供，有路径检查，不能跳出这个目录。

### 给 agent 的读取方式

- **待办清单** `export.md`：按页面分组；组内高优先级在前。每条包含：
  - 编号、类型、优先级、状态、作者、时间；
  - 引用的位置文字；
  - CSS 选择器和屏幕尺寸；
  - 附件地址；
  - 正文和全部讨论。

  样例见 [export-sample.md](export-sample.md)。agent 拿到这份清单就能定位并修改，不需要再问「是哪里」。
- **全部数据** `export.json`：用于统计和复盘。
- **回写**：改完 `POST items/<id>/review` 提交验收，署名 `X-FB-Name: Claude`（或 Codex）。汇总页按署名把 AI 的回复显示成单独的样式。

### 验收

「agent 说改好了」和「人认可了」是两件事，所以分成两个状态。

- **状态**：待处理 → 处理中 → 待验收 → 已改好。改动在预览环境时，中间多一步「已通过」，等 agent 上线后再变成已改好。
- **验收包**：agent 提交时带上改了什么（必填）、预览地址、改后截图，以及改动在预览环境还是已在线上。它是一条 `kind='review'` 的回复，预览地址和阶段记在 `meta` 里，截图是挂在这条回复上的附件。
- **谁能验收**：只有管理员口令能调用 `accept` 和 `reject`。团队口令（也就是 agent 用的口令）把状态写成 `done` 时，服务端会把它转成提交验收，所以按旧办法写的 agent 不用改也不会绕过验收。
- **打回必须写理由**。这句话是整个流程里信息量最大的东西：它是在具体任务上、针对具体产出、当场说的。`GET corrections.jsonl` 把每次打回导出成一行，包含任务原文、agent 当时交的说明、打回的原话。
- **通过即可上线**：预览环境的改动通过后进入「已通过」，并出现在 agent 的待办清单里；agent 发布后调用 `publish`。上线这个动作由 agent 在项目自己的发布流程里做，本服务只记录「谁在什么时候同意了哪一版」。
- **关闭**：`FB_ACCEPTANCE=0`，回到任何人都可以直接标「已改好」。

## 四、为什么这样设计

- **意见要落在页面上**：「哪里」比「什么」更难说清。点选加截图把「哪里」固定下来，agent 就不会改错地方。
- **人和 agent 用同一套记录**：批注、讨论、修改说明都在一条线上，复盘时不用去翻聊天记录。
- **轻量**：一个 Python 文件、一行 `<script>`，任何项目当天就能接入。没有账号系统和前端构建，出了问题也容易排查。
